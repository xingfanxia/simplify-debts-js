# 微信共享分账房间 V2：先建房、再邀请、共同记账

## 产品结论

共享账单应当是一种独立的房间模式，不是把一张已经完成的本地账单迁移上云。

用户可以从空白状态创建共享账单，把邀请卡片发到现有微信群；每个微信用户点击后以自己的微信身份加入，并自动成为账单参与人。房间允许零支出开始，成员加入后各自添加支出。默认流程不再要求先添加两个人、一笔支出、填写显示名称或认领参与人。

普通本地账单继续保持完全离线，两种模式互不自动上传或转换。以后如确实需要“导入本地账单”，应作为显式的独立功能设计，不得重新污染默认建房流程。

## 已核实的平台与代码事实

- 当前 `main@b1ff9a2` 的共享入口依赖本地已有至少两人和一笔支出；创建与加入都使用“显示名称 + 参与人认领”。相关代码位于 `miniprogram/pages/index/index.js`、`miniprogram/pages/room/room.js` 和 `cloudfunctions/ledger/service.js`。
- CloudBase 云函数可通过 `cloud.getWXContext().OPENID` 获得不可由客户端伪造的微信用户身份。身份判断继续只在服务端完成。
- 本版本不采集真实微信头像。昵称通过 `input type="nickname"` 由用户确认；头像位置统一显示根据昵称生成的首字母占位，避免引入云文件存储、临时 URL、清理规则和额外隐私申报。
- 正式 CloudBase 环境 `cloud1-d3gbdocpk8fcb2e97` 已存在六个私有集合、`ledger` 与 `ledger_cleanup`。任何新的生产 schema、函数部署、存储规则或小程序上传仍需单独确认。

## V2 用户流程

### 房主

1. 首页始终提供清晰但克制的“新建共享账单”入口，不依赖本地参与人或支出。
2. 房主填写账单名称、币种和账单内昵称。
3. 昵称只用于房间内显示，不参与身份判断；界面根据昵称生成首字母占位头像。
4. 服务端以当前请求的 `OPENID` 创建 owner、对应 participant 和空房间；客户端传入的 OpenID、角色或 memberId 一律无效。
5. 房主点击“发送邀请”，把带高熵 token 的小程序卡片发到现有微信群。

### 被邀请成员

1. 点击卡片后只看到房间名称、币种、当前成员数和隐私提示，不看到成员资料、支出、余额或结算。
2. 服务端用当前请求的 `OPENID` 判断是否已加入。
3. 新用户确认一次账单内昵称后点击“加入”；不认领任何已有名字。
4. 加入事务自动创建一个 editor member 和与其一一对应的 participant；重复点击或弱网重试不得产生重复成员或参与人。
5. 已加入用户再次打开同一邀请，直接进入房间；已过期、撤销或耗尽的邀请不能授权新成员。

### 共同记账

- 每位有效成员都可以新增、编辑和删除支出。
- 新增支出的付款人默认是自己，也可选择其他有效成员。
- 分摊对象默认全体当前参与人，也可自定义。
- 房间页面打开时继续采用立即刷新、`onShow` 刷新和约 2.5 秒前台轮询；离线只读。
- 房主控制邀请、移除成员、归档和删除；普通成员可以退出。
- 被移除或退出的成员立即失去后续云端访问。已经同步到设备的旧缓存无法远程擦除，重新联网后清除。

## 身份、成员和参与人模型

### 不变量

- `OPENID` 只在云函数请求期间使用，不写入应用集合、不返回客户端。
- 成员鉴权键继续由 `roomId + OPENID` 的单向哈希派生；roomId、memberId、participantId 都不是授权凭证。
- 每个有效微信 member 默认且仅对应一个 participant；加入、退出、移除必须维护这一关系。
- member 决定访问权限和角色；participant 只参与支出与结算计算。
- 客户端提供的昵称、角色、owner、memberId、participantId 都不能改变调用者身份或权限。

### 建议字段调整

| 集合 | V2 关键变化 |
|---|---|
| `ledger_rooms` | 允许空 `expenseDocIds`；创建时只有房主 member/participant；保留 revision 和文档 ID 索引 |
| `ledger_members` | 保留房间级身份哈希键和房间昵称；`participantId` 创建时自动绑定，不再认领 |
| `ledger_participants` | 增加 `memberId`/`kind: member` 关系；名称来自该成员确认的昵称；不再由加入页认领 |
| `ledger_expenses` | 付款人与分摊人只引用当前有效 participant；仍保存创建者和更新时间用于审计/冲突处理 |
| `ledger_invites` | 保持 token 哈希、过期、撤销、次数限制；预览不得返回成员资料或账单事实 |
| `ledger_mutations` | 继续保护建房、加入、资料更新和支出写入的幂等性 |

不增加全局用户资料集合。昵称按房间保存，避免为了便利建立跨房间可关联的用户画像。真实头像不上传、不存储；如果以后要增加头像或跨房间复用资料，必须重新评估隐私声明、文件访问和删除语义。

## 昵称与隐私边界

资产包括微信身份、昵称、房间成员关系、邀请 token 和账单事实。参与者包括房主、受邀用户、已加入成员、被移除成员、非成员和 CloudBase 管理端。

- 昵称是用户控制的不可信输入，服务端必须校验必填与 28 字符上限，展示层不得把昵称当 HTML 或权限字段解释。
- 邀请预览不得返回昵称列表、支出、余额或内部标识。
- 昵称只按房间保存；成员退出/被移除后，历史昵称随账单保留，直到房主删除并经过 30 天恢复窗清理。
- 客户端只生成首字母占位头像；系统不请求、上传、保存或返回真实头像及云文件引用。
- 隐私保护指引必须披露用户主动提供的昵称、共享账单成员关系、用途、访问对象、30 天删除窗和联系方式。

## 服务端动作契约

- `room_create`：输入房间名、币种、取整偏好和用户确认的资料；创建空房间、owner member 与 owner participant。
- `room_invite`：仅房主生成可撤销、可过期、有限次的分享路径。
- `room_join_preview`：只返回最小房间摘要和邀请状态。
- `room_join`：用服务端微信身份幂等创建 editor member 与 participant；不接受认领参数。
- `room_get`：先验证 membership，再返回账单、成员与经授权的资料视图。
- `room_profile_update`：成员更新本房间昵称，并同步其 participant 名称。
- `room_mutate`：有效成员修改参与计算的支出事实；payer 默认值只由客户端体验决定，服务端仍验证引用。
- `room_manage`：房主移除成员、撤销邀请、归档或删除；成员退出。

删除旧的 `claimParticipantId`、`newParticipantName` 和“认领身份”协议。服务端应明确拒绝试图借这些旧字段指定他人身份的请求，避免兼容代码重新引入权限混淆。

## UI 信息架构

- 首页本地模式保持原有工具布局，在顶部操作区提供一个始终可见的“新建共享账单”入口。
- 创建弹层只包含：账单名称、币种、昵称和创建按钮；不展示本地参与人列表或头像授权。
- 邀请落地页采用单一主操作：确认昵称后加入；不出现身份列表或头像授权。
- 房间页把成员、支出和结算作为三块核心工具内容；资料设置属于成员自身，不放进房主管理菜单。
- 视觉继续采用克制、现代、中文工具型风格；优先保证 320–430px 视口的点击面积、可读性和信息密度。

## 迁移与发布顺序

1. 先只读检查生产集合是否已有房间数据。
2. 如果没有真实房间数据，直接部署兼容 V2 的字段与函数，不删除集合。
3. 如果已有数据，先写兼容读取或明确迁移方案；任何批量修改、删除或不可逆清理必须另行确认。
4. 本地完成服务端契约、客户端流程、权限负向测试和开发者工具视觉验收。
5. 更新隐私保护指引后，再分别取得云函数部署和小程序上传授权。
6. 使用两个真实微信账号完成建房、群分享、昵称加入、共同编辑、移除和撤权验收。

## 验收重点

- 空白首页可直接创建零支出的共享账单。
- 创建者自动成为房主和参与人，不出现身份认领。
- 群友打开邀请后只需确认昵称并加入；服务端自动创建唯一 member/participant。
- 同一微信账号重复加入不产生重复数据。
- 每位成员都能添加支出，付款人默认自己；另一端 3 秒内看到更新。
- 非成员、过期邀请持有者和被移除成员无法读取完整房间或成员昵称。
- 昵称不出现在邀请预览或日志中；客户端与服务端协议不包含真实头像或云文件引用。
- 本地账单不因共享入口而上传，且所有原有功能无回归。
